## Summary

Decision: a new block `import` is one card. It has [choose file] and a [download template] link. The picked file uploads through the app's file handler, the same one upload fields use. The app's server reads the file and sends back the column match, a sample of the rows and every row error. Changing a column or a sheet asks the server again. Confirm sends one action (the file's id, the sheet and the match, not the rows), and the app answers with a count and, if it wants, a left-out rows file. blocks reads and writes no .xlsx or .csv and adds no dependency. The template, the left-out rows and a table's .xlsx export are all files the app sends. Default look, no new colour.
Screens: the flow (empty, uploading, the server reading, file read with columns and rows, row errors), the finish (confirm, sending, done, the app refusing rows), and every other state (upload failed, the server not answering or refusing the file, wrong columns and re-checking, several sheets, Thai, off, JavaScript off, a table's export). Each is drawn light and dark, at 1440 and 390.
Open questions: none. This kind needs about 650 lines, which fits the cap's 1,740 lines of headroom after the open PRs, so no cap raise is needed.

## For impl

- Wire name `import`. That is a keyword in JS and Swift, so the generated types are `Import` (Rust, TS), and the Swift case is written with backticks. What the screen declares: `id`, `title`, `into` (the words' target name), `columns`, `accept`, `mb`, `template` (a link: name and src, the same shape as an upload field's file), and `read` and `action` (the two action ids). A column has `key`, `label`, `type` (text, number, money, date, choice), `required` and `values`. Matching by other header names is the server's job.
- The server's answer to `read` is a patch on the block, `sheet`: the file (id, name, size, rows, sheet, sheets), the headers, the match (column key to header), the samples, the extras, the first rows (spreadsheet row number and cells), every bad row with its reasons by column key, or an `error` (the file can't be used). The answer to the import action is `done` (count, left, an optional left-out file link), or `error` plus `refused` rows (all or none).
- Both actions carry `{file, sheet, map}`. Both are idempotent: a retry or a back-and-forth sends the same thing.
- On the web, the kind's view is the only new code (about 220 lines). With no parser, there's nothing big left to split off. It loads as its own chunk on first draw, like the other lazy kinds, so the screen bundle doesn't grow until the kind is used. The preview reuses the table kind's DOM and CSS (`.tbl`) and the upload field's file handler and `.pgt` bar.
- `import.css` here (tokens only) is all the kind adds. One container query puts the columns beside the rows at 880 px and wider, and one folds them below 600 px. `import.js` and `data.js` are a preview-only port with the English and Thai words. `page.css` is only for these previews. Run `./render.sh` (Playwright's cached headless Chromium) to make the images.
- Fixtures: the parser fixtures in the AC become server-answer fixtures (a good read, bad rows, wrong columns, a refused file), shared by the web, HTML and Swift tests.
- Line estimate: Rust kind and words about 110, the static HTML about 60, the web view about 220, Swift (picker, upload, preview and confirm) about 200, codegen about 50. That is about 650 against 1,740 lines of projected headroom (`drover cap blocks`: 39,760 of 41,500 with the open PRs).
